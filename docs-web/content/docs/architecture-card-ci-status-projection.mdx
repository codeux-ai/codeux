# Card CI Status Projection

Task, Sprint, and Live cards expose one compact persisted `ciStatus`: `pending`, `running`, `failed`, or `null` after settlement. The projection does not load the large remote Git status snapshot and does not poll GitHub or GitLab.

## Persisted evidence

Code UX batch-loads the latest `ci_gate_status` event per task within its sprint's latest run, the latest `main_merge_gate_status` event from that run, and active `open` or `claimed` CI repair attention. Ordering uses the event timestamp and event identity so restart-style reads are deterministic. Earlier sprint-run gates and run-linked attention stay in audit history but cannot become the current attempt's stage. Unlinked gate evidence remains compatible when recorded after the latest run began, and unlinked attention remains available for durable/manual handoffs.

Only the compact status crosses the card contract. Failed logs, credentials, and arbitrary attention payload fields remain internal.

## Resolution rules

| Evidence | Card status |
| --- | --- |
| Durable task `merge_indicator = CI` without usable newer detail | `pending` |
| Latest task or main-merge gate is waiting on checks | `running` |
| Failed checks, blocked task gate, or active CI repair attention | `failed` |
| Review-only main-merge blocker without failed checks | `null` |
| Gate settled or relevant attention resolved | `null` |

Sprint cards aggregate their task statuses and latest main-merge gate with failure-before-running-before-pending precedence. Task cards and Live subtasks call the same pure resolver, so all three surfaces interpret persisted state identically.

Sprint lifecycle and QA follow the same attempt boundary. Cancellation-pending remains active and displays as running until shutdown reaches the terminal cancelled state, including in project activity and compact active-task reads. Active run states remain authoritative; after a run is terminal, a newer explicit sprint update such as manual completion or a later operator pause takes precedence. Task and sprint `latestReview` values come from the latest sprint run; an unlinked legacy or manual verdict is retained only when it was recorded after that run began. Recovery rows from the same reviewer and QA cycle collapse to the latest attempt before blocker precedence is applied across distinct reviewers, so a passing recovery replaces its own interrupted row without hiding another reviewer's blocker. A new sprint attempt does not inherit an older attempt's QA or merge stage.

Review gating remains separate from CI failure presentation. A main-merge `review_blocked` event becomes `failed` only when it also carries failed-check evidence or matching CI repair attention is active.

The dashboard combines that evidence with lifecycle and latest-review state in durable workflow flows. Task, Live, and Overview cards use **Coding**, **Pull request**, **QA**, **CI**, **Merge**, and **Completion**. Sprint gallery and ledger cards use **Planning**, **Coding**, **QA**, **Pull request**, **CI**, **Merge**, and **Completion**. The sprint Planning stage follows the latest sprint-scoped planning invocation, including the interval before tasks exist. CI evidence enriches the later stages but is optional, so a Sprints refresh without historical gate events cannot unmount or flash away the badge. A durably completed workflow settles missing historical PR, checks, and merge projections as successful rather than showing contradictory pending stages. A newer successful observation replaces stale failure, while active matching CI attention restores the failure state.

Active, task-matched human-only attention has presentation precedence over the ordinary lifecycle and gate summary: the trigger becomes red **Human needed** while its disclosure retains the task's six stages or the sprint's seven stages. Explicit attention-item evidence is required: status is `open` or `claimed`, owner is human/user, and worker assignment is explicitly empty. Cleared, machine-owned, worker-assigned, sibling-task, and sibling-sprint attention does not. Sprint-run summaries alone never qualify because they omit status and assignment and may come from generic pause/error events.

The lean execution snapshot carries this evidence in `sprintWorkflowProjections`, separate from bounded activity feeds. Planning is selected by invocation start/creation identity rather than heartbeat updates, and strict human intervention is queried across every active task attention row rather than the 50-item dashboard feed. This keeps Planning and **Human needed** stable on very large sprints.

The bright interactive badge opens one viewport-positioned interaction region on a lightly translucent, blurred outer surface. Generic lifecycle-only badges are announced as workflow status/details; CI labels are used only when CI evidence exists. Repeated trigger activation closes the disclosure. Its opaque Delivery flow card contains the circular rail; a floating responsive arrow points to the opaque QA review card when a review exists. Status circles share the vertical center of their stage entries, and each connector begins from that aligned marker. Requested changes use the blue pencil and **QA edits** treatment even when failed-check evidence also exists; red identifies actual provider/runtime/workflow failures and explicit **Human needed** intervention. Live replaces its separate task lifecycle and QA badges, while Task, Sprint, and Overview surfaces keep their surrounding lifecycle context and replace the standalone QA/CI disclosures. During active, failed, or cancelled Planning, stale task QA/CI evidence is suppressed from visible, accessibility, and data state. During active coding below 100%, the sprint badge stays on Coding and ignores child-task gate aggregation; at 100%, current-run sprint QA and explicit final CI/merge evidence become visible. Completion percentage alone never claims Merge. An authoritatively completed task suppresses historical failed, cancelled, or changes-requested QA from its current badge and review action while retaining the audit rows; active running and passing QA remain visible as current or positive evidence. Terminal lifecycle state wins over stale evidence, and active human-only intervention keeps presentation precedence. Each unsettled task badge continues showing its own PR, QA, CI, and Merge transitions.

The deterministic dashboard integration suite replays these outcomes across all four card renderings, including keyboard-only QA details, collapsed follow-up specifications, Escape focus restoration, unrelated-event isolation, and unchanged snapshot replay. It mocks runtime boundaries and does not invoke Docker, provider CLIs, Git hosting, or a live database.

## Compatibility and troubleshooting

`ciStatus` is optional and nullable. No schema migration or new setting is required; the projection uses existing task, event, sprint-run, QA-review, and attention tables. Malformed payload JSON is ignored safely. If a badge remains after CI settles, verify that the latest run has a newer settled gate event and that CI repair attention is no longer `open` or `claimed`.
