# External Chat Providers

Code UX connector profiles declare setup, provider-native or bridge transport, ingress authentication, identity, verification, and session requirements. Shared services own encrypted secrets, authorized project routing, durable idempotency, outbound leases, cancellation/recovery, and redacted diagnostics.

Registry presence is a typed software contract. It is not provider certification, certification of an operator-selected bridge, or proof that a connection is production-ready.

## Transport boundaries

- `official_api` uses profile-pinned provider endpoints for WhatsApp, Telegram, Slack, Microsoft Teams, or Discord.
- `managed_bridge` and `webhook` use operator-configured HTTP endpoints.
- `native_bridge` executes an operator-configured local command with no shell. iMessage has managed/native bridge modes only; there is no Apple personal-iMessage bot endpoint.

Unsupported provider/mode pairs fail validation. Existing bridge records keep their endpoint meaning when official support is added.

## Six-provider contract matrix

### Setup, ingress, identity, and outbound

| Provider | Modes | Required native setup/secrets | Ingress authentication | Identity | Outbound endpoint |
| --- | --- | --- | --- | --- | --- |
| Meta WhatsApp | managed, webhook, official | Graph version, phone-number ID; access token, app secret, verify token | GET verify-token challenge; POST `X-Hub-Signature-256` over exact raw body | `phone_number_id` channel, inbound `wamid`, sender recipient | Fixed `graph.facebook.com/{version}/{phoneNumberId}/messages` |
| Apple iMessage | managed, native | Bridge workspace/device + API key, or command/directory + bridge token | Code UX fresh timestamp, bearer token, and replay nonce for bridge callbacks | Opaque normalized chat/message GUIDs | Configured third-party bridge or protocol-v1 command; no Apple endpoint |
| Telegram | managed, webhook, official | Bot username; bot token and webhook secret token | Exact `X-Telegram-Bot-Api-Secret-Token` | `update_id`, chat/message IDs, `message_thread_id` | Fixed `api.telegram.org/.../sendMessage`; token-bearing URL never persisted |
| Slack | managed, webhook, official | App/workspace metadata; signing secret and bot token | Slack `v0` HMAC, exact raw body, five-minute timestamp | Outer `event_id`, channel, `ts`/`thread_ts` | Fixed `slack.com/api/chat.postMessage` |
| Microsoft Teams | managed, webhook, official | App ID/type, required tenant policy, client secret | Bot Connector JWT, claims, endorsement, tenant, documented service URL | Activity/conversation/reply and authenticated conversation reference | Fixed OAuth authority plus validated Activity `serviceUrl` reply path |
| Discord | webhook, official | App ID, Ed25519 key, intents, bot token | Ed25519 HTTP interactions; authenticated Gateway session | Snowflake message/channel/thread IDs; self-message suppression | Fixed `discord.com/api/v10`; secure Discord-owned Gateway/resume hosts |

### Verification, retry/idempotency, sessions, and limitations

| Provider | Verification/test eligibility | Retry/idempotency | Session/reconnect | Limitation |
| --- | --- | --- | --- | --- |
| Meta WhatsApp | Read-only phone resource check; sends require explicit Meta test-number opt-in | Durable `wamid` dedupe; sanitized Graph retry classification | Stateless webhook | Opt-in test number is not production readiness |
| Apple iMessage | Third-party bridge/protocol check only; no official public bot sandbox | GUID dedupe, leases, process timeout/cancellation | Operator bridge owns session | No official API, Apple certification, database access, or AppleScript claim |
| Telegram | `getMe` + read-only `getWebhookInfo`, requiring test credentials | Durable update dedupe; exact 429 delay; ambiguous dispatch is terminal | Stateless webhook | 4,096-character `sendMessage`; operator sets webhook |
| Slack | `auth.test`, requiring test credentials | `event_id` dedupe, immediate durable acknowledgement, pacing/`Retry-After`; ambiguous send terminal | Stateless Events webhook | Scopes, installation, membership remain provider-controlled |
| Microsoft Teams | Deterministic Emulator-shaped/mocked contract coverage; no public unauthenticated sandbox | Activity dedupe; transient/429 retry; invalid trust input terminal | Durable conversation reference; memory-only OAuth | Localhost is not an official Connector service URL |
| Discord | Read-only current-user check, requiring test credentials | Event dedupe plus stable outbound nonce/lease and route/global rate limits | Gateway heartbeat, Resume/Identify, bounded reconnect | `MESSAGE_CONTENT` is privileged |

A credential-gated test that skips is **not run**, not passed.

## Security and lifecycle

New secrets are AES-256-GCM envelopes. Public connection records expose configured-state placeholders only; runtime services resolve plaintext ephemerally. Startup migrates legacy plaintext rows only after secure key readiness, seals before compare-and-set commit, and clears legacy JSON only after success. Partial failures remain resumable. Database rollback requires the matching key-provider version; never restore secrets to plaintext.

Secret replacement/clearing, mode changes, and setup changes invalidate verification. Display-name, enabled, and status-only edits preserve it. Remote connection mutation/verification requires TLS, `credential_admin`, and explicit remote credential management. Bindings and deliveries authorize against their stored project.

MCP destructive/transport changes and manual resend use exact-payload, one-use approval. REST resend requires `{ "approval": { "confirmed": true } }`.

Generic signed/nonce-bearing callbacks use durable replay receipts. Provider-native callbacks use their own Meta, Telegram, Slack, Teams, or Discord authentication. The normalized external message ID is then atomically inserted; only the insertion winner can post to chat. Immediate callbacks acknowledge after durable acceptance. Ambiguous shared-channel routing is stored instead of guessed.

Outbound workers use expiring compare-and-set leases, bounded timeouts, capped retry backoff, provider retry hints, and abort signals. Shutdown releases owned leases, terminates native command groups, stops reconnect timers, and settles jobs. Startup independently recovers ingress, due deliveries, and resumable sessions. Optional connector failure does not fail global readiness.

Connector health reads persisted sanitized outcomes without provider calls. Public delivery records omit payload and lease fields. Expired receipts/sessions are cleaned up; connection deletion cascades bindings and deliveries.

## REST and MCP controls

Canonical handshake/callback URL:

```text
GET  https://codeux.example.test/api/chat-providers/ingress/connection-example
POST https://codeux.example.test/api/chat-providers/ingress/connection-example
```

REST verification, approved retry, and cancellation:

```text
POST /api/chat-providers/connections/connection-example/verify
POST /api/chat-providers/deliveries/delivery-example/retry
POST /api/chat-providers/deliveries/delivery-example/cancel
```

```json
{ "approval": { "confirmed": true } }
```

Verification failures are sanitized:

```json
{
  "status": "failed",
  "providerErrorCode": "verification_timeout",
  "retryable": true,
  "issues": ["Provider verification timed out."],
  "diagnostics": null
}
```
